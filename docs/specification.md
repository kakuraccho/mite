## 1. エグゼクティブサマリー

Miteは、PC操作の途中で「次に何を、どの順番で行うか」が分からなくなる高齢者を、離れた家族が支援するサービスである。現在の具体的な対象は80歳の祖父であり、本人ができる操作は本人が行うことを基本とする。

Miteが目指す中心の循環は次のとおりである。

```
家族に支援してもらう
        ↓
解決方法をガイドとして残す
        ↓
次回はガイドを使って一人で操作する
        ↓
難しければ、途中の状況を引き継いで再び家族に相談する
```

現時点では、支援開始から終了までの正常系は一度整理済みである。一方、Mite全体の体験を一周させるために、次は「支援からガイドを作る正常系」と「後日そのガイドを使う正常系」を決める。プロトタイプでこの正常系を検証した後、分岐・異常系・端末間の状態ズレ、保存情報、技術調査、技術設計の順に進める。

## 2. プロダクト概要

### 2.1 対象ユーザー

**ステータス: 確定**

- 現在の具体的な対象は、日常的にPCを使う80歳の祖父である。
- 祖父はAmazonで買い物をしたり、航空券を予約したりできるため、デジタル操作全般ができないわけではない。
- 見慣れない画面、複数画面の行き来、操作順の判断で詰まりやすい。
- 実画面やスクリーンショットで操作場所と手順が示されれば、自分で操作できるという本人ヒアリングがある。

本書では、役割名を次のように表す。

| 役割名 | 意味 |
| --- | --- |
| **利用者（祖父）** | PC操作で支援を受ける人。現時点の具体的な検証対象は祖父。 |
| **家族** | 利用者を遠隔で支援する人。現在は叔父・孫を想定。 |
| **Mite** | 支援依頼、接続、画面共有、マーキング、記録、ガイド利用を仲介するシステム。 |

将来、祖父以外の高齢者へどこまで一般化するかは未決定である。

根拠: [PS]「あなたが深く知る『たった一人』はだれ？」「課題」

### 2.2 解決する課題

**ステータス: 確定**

利用者側の中心課題は、マウス操作や文字入力そのものではなく、現在の画面から目的を達成するために「次に何を、どのような順番で操作すればよいか」を考える負担である。

代表例は認証コード入力である。利用者はメールを開き、コードを紙に控えるところまではできるが、元の購入画面へ戻る方法が分からず、時間切れやコード再発行を繰り返して混乱することがある。

支援者側には次の課題がある。

- 近くにいる叔父は仕事の合間で支援時間が短く、代わりに操作して早く解決しがちである。
- 代行だけでは、次回同じ問題が起きたときに使える知識が利用者へ残らない。
- 時間をかけて支援できる孫は離れて暮らしており、必要なときに対面できない。

したがって、Miteが解くのは単なる物理的距離ではなく、**必要なときに、本人のできることを奪わず、次回につながる形で支援を受けにくいこと**である。

根拠: [PS]「次に行うべき操作が分からない」「助けられる人との物理的な距離と、繰り返し発生する問題への対応」

### 2.3 Mission / Vision / Value

**ステータス: 確定**

- **Mission**: 離れていても、家族がそばにいるように支えられる環境をつくる。
- **Vision**: デジタルが苦手になっても、信頼する人とのつながりを失わずに使い続けられる状態を目指す。
- **Value**
    - 信頼や安心に関わる部分は人、整理や反復作業はAI。
    - 本人ができることは奪わない。
    - 助けを求めるための操作を増やさない。
    - 家族に迷惑をかけていると感じさせない。

根拠: [PS]「このサービスのMVV」

### 2.4 提供価値と独自性

**ステータス: 確定**

Miteの価値は、画面共有、マーキング、手順作成という単体機能の新規性ではなく、次の体験を一つにつなぐことにある。

1. 困った利用者が、少ない操作で家族へ支援を求める。
2. 家族が実際の画面を見ながら、言葉と視覚的な印で次の操作を伝える。
3. 利用者本人が操作して問題を解決する。
4. 繰り返し役立つ支援だけをガイドとして残す。
5. 次回、利用者がそのガイドを使って一人で操作する。
6. ガイドで解決できなければ、どの手順で詰まったかを引き継いで家族支援へ戻る。

AIは家族の代わりに判断・支援する存在ではなく、支援内容の整理や反復作業を補助する位置付けとする。ただし、MVPでAIをどの工程に使うかは未決定である。

次の主張は、現時点では未検証である。

- 既存の画面共有・遠隔支援・手順作成サービスを組み合わせることが、祖父にとって実際にどれほど負担か
- 家族の顔が見えることが、安心感、支援しやすさ、「迷惑をかけている」という感覚の軽減につながるか

根拠: [PS]「解決策の全体像」「既存サービスとの違い（独自性）」

### 2.5 非目標

**ステータス: 確定**

- 利用者が一人で何でもできる状態にすること自体を目的にしない。
- 家族が最初から全操作を代行する体験を中心にしない。
- AIで家族を置き換えない。
- すべての支援記録を無条件にガイド化しない。
- 単体機能の多さをMiteの価値にしない。

## 3. 決定状況の要約

### 3.1 確定事項

- 対象ユーザーの具体例は80歳の祖父である。
- 中心課題は「次の操作と順番が分からないこと」である。
- 家族が離れた場所から支援し、本人ができる操作は本人が行う。
- 支援では、家族が利用者の画面を見て、視覚的な印で操作場所を伝える。
- 一度の支援をその場で終わらせず、役立つ支援をガイドとして残し、次回利用する循環を作る。
- ガイドとして残す価値があるかは、AIではなく利用者を知る家族が判断する。
- ガイドで分からなくなった場合は、該当ガイドとステップの情報を引き継いで家族支援へ切り替えられる体験を目指す。
- 音声文字起こし、遠隔操作、ガイド利用中のAI支援、支援中のインカメラ、ガイドのAI検索はMVP外とし、将来の展望として扱う。

### 3.2 仮決定事項

- 画面左端に常時4px程度のバーを表示し、マウスを乗せると支援依頼パネルを展開する。
- 支援依頼時に全画面スクリーンショットを取得し、任意コメントを添付する。
- 家族は通知と利用者のオンライン状態を確認し、支援可能な時点でMiteから電話をかける。
- 支援中は音声通話、画面共有、家族のクリック位置を利用者側へ表示するマーキングを使う。
- 支援中、ガイド作成材料として画面を定期取得する。取得間隔は未決定であり、5秒間隔は[SF]にある検証候補とする。
- 解決後、家族側にガイドを作るかどうかの選択を表示する。
- ガイドを作る場合、Miteがスクリーンショットをもとに仮ガイドを用意する。
- 仮ガイドは利用者と家族が一緒に確認し、編集操作は家族側で行う。
- ガイドは、理解しやすいタイトルと代表スクリーンショットを持つ一覧から選ぶ。
- ガイドは一度に全手順を見せず、原則として1ステップ1操作で表示する。
- ガイドは別ページだけで読ませず、実際の操作画面の右上や小さな常駐ウィンドウに表示する案を第一候補として検証する。
- ガイドの粒度は、まず「認証コード」のような目的別のまとまりを採用し、サービスをまたいで通用する範囲を検証する。

根拠の内訳:

- 支援依頼からガイド保存までの案: [SF]全体フロー
- タイトル・代表画像・1ステップ1操作・目的別の粒度: [PS]「手順ガイド」「予想されるユースケース」「コメントを踏まえて」
- 小型常駐ウィンドウと手動の「次へ」: [CV]のプロトタイプ案

### 3.3 未決定事項

- Miteを開く方法と、常駐UIが普段の操作を邪魔しない条件
- 家族がすぐ対応できない場合の待機・予約・再通知・期限切れの扱い
- 支援依頼の取消、重複防止、自力解決時の扱い
- 支援開始時に必要な利用者の同意と、画面共有開始のタイミング
- 支援依頼・接続・支援・終了に関する正式な状態名と遷移
- 音声通話、画面共有、マーキングの一部だけが失敗した場合の扱い
- ガイド作成に使う情報、取得頻度、選択方法、保存期間
- 仮ガイドをAIで生成するか、ルールベース・手動・固定モックで作るか
- AIを使う場合の送信対象、マスキング、同意、モデル、保存方針
- ガイド作成フローを、家族の負担が小さい工程数へどう短縮するか
- ガイドのタイトル、画像、説明、ステップ分割を誰がどこまで編集できるか
- 利用者もレビューに参加する必要があるか
- ガイド保存後に利用者側へ反映するタイミング
- 「認証コード」のような目的別ガイドが、Amazon・JALなどサービスの異なる画面でも通用する範囲
- ガイド利用時の表示位置、サイズ、最前面表示、画面切替方法
- 次のステップへ手動で進むか、操作完了を自動検知するか
- ガイドの中断・再開・完了・削除・更新の扱い
- MVPの対象OS。Windowsを採用する場合の対応バージョン、画面解像度、表示倍率
- 認証、家族との紐付け、アクセス権限、セキュリティ、プライバシー

### 3.4 将来の展望

**明示的にMVP外とする機能**

- 音声文字起こし [SF]
- 遠隔操作 [PS][SF]
- 「ガイドに沿って操作する」ときのAI支援 [PS][SF]
- 支援中のインカメラ投影 [PS][SF]
- ガイドのAI検索 [PS][SF]

[PS]の初期ユースケースでは、AI検索に自然文・音声入力を使う案がある。ガイド数が増え、一覧から探す負担が実際に問題になった時点で再検討する。

**将来候補・時期未決定**

- 現在画面を認識し、保存済みの画像だけでなく実画面上にも案内を重ねる機能 [PS]
- 同じステップで支援への切替が繰り返されたとき、利用実績からガイドを改善する機能 [PS]

遠隔操作を再検討する場合は、「本人ができることは奪わない」という方針に従い、本人の許可、操作中の明示、本人による停止を要求候補として設計し直す。

## 4. MVPの範囲

### 4.1 MVPで成立させる体験

**ステータス: 仮決定（MVPで成立させる体験案）**

MVPでは、少なくとも次の3本の正常系が途切れず説明・デモできる状態を目指す。

#### Flow A: 家族に支援してもらう

```
困る
→ 支援依頼を送る
→ 家族が内容を確認する
→ 家族が発信し、利用者が応答する
→ 音声・画面共有・マーキングで支援する
→ 解決する
→ 支援を終了する、またはガイド作成へ進む
```

#### Flow B: 支援をガイドにする

```
解決する
→ ガイドを残すか家族が判断する
→ ガイドの下書きを作る
→ 内容を確認し、必要なら修正する
→ 保存する
```

#### Flow C: 後日ガイドを使って一人で操作する

```
同じ、または似た操作で困る
→ 保存済みガイドを探す
→ ガイドを開始する
→ 1ステップずつ確認しながら実際のPCを操作する
→ 全ステップを完了する
```

ガイドで分からなくなった場合は、次のフォールバックも一つの正常な体験として扱う。

```
ガイドの途中で分からなくなる
→ 「家族に聞く」を選ぶ
→ ガイド名と現在のステップを含む支援依頼を送る
→ Flow Aへ移る
```

### 4.2 MVPで固定しないもの

技術調査前に、次の事項を特定技術へ固定しない。

- 通信方式、画面共有方式、音声通話方式
- クライアント・サーバー構成
- API、イベント、DBの詳細
- AIモデル、LLM、画面認識方式
- Windows APIやUIフレームワーク

プロトタイプでは、実通信、実スクリーンショット、AI生成、サーバーをモックにしてよい。目的は実装方式の証明ではなく、体験と仕様の不足を発見することである。

## 5. 支援開始から終了までの正常系

**全体ステータス: 仮決定**

この章は[SF]で整理済みの現在案である。正常系としてプロトタイプへ反映するが、ユーザー検証・技術調査前のため確定仕様とはしない。

| # | 出来事 | 利用者（祖父） | 家族 | Mite |
| --- | --- | --- | --- | --- |
| 1 | 困りごと発生 | PC操作中に困る。 | - | - |
| 2 | 支援UIを開く | 画面左端へマウスを移動し、展開したボタンを押す。 | - | 左端に約4pxのバーを常時表示し、マウスオーバーでパネルを展開する。 |
| 3 | 困りごとを記録 | 状況コメントを任意で入力する。 | - | 全画面スクリーンショットを取得し、コメント入力ダイアログを表示する。 |
| 4 | 支援依頼を送る | 送信後は待つ。 | 通知を受け取る。 | スクリーンショットとコメントを一つの支援依頼として記録し、家族へ通知する。 |
| 5 | 通知を確認する | 待つ。 | 受け取った通知を開く。 | 支援依頼の内容を表示する。 |
| 6 | オンライン状態を確認する | 待つ。 | 利用者のオンライン状態を見る。 | 利用者のオンライン状態を取得・表示する。 |
| 7 | 家族が発信する | 着信を待つ。 | 支援できるタイミングでMiteから電話をかける。 | 2人の接続を開始する。 |
| 8 | 支援開始 | 電話に出る。 | 接続を待つ。 | 支援セッションを開始する。 |
| 9 | 利用者側を準備する | 待つ。 | 待つ。 | 利用者側で画面共有とオーバーレイを開始する。 |
| 10 | 家族側を準備する | 待つ。 | 利用者の共有画面を確認する。 | 家族側へ共有画面を表示し、マーキングを使える状態にする。 |
| 11 | 状況を再現する | 問題箇所へ到達できるところまで自分で操作する。 | 共有画面を確認する。 | 画面共有と音声通話を継続する。 |
| 12 | 操作支援 | 家族の説明とマーキングを参考に、自分で操作する。 | 共有画面上をクリックして場所を示し、音声で説明する。 | 家族側のクリック位置に応じて、利用者側へマーキングを表示する。 |
| 13 | 支援記録 | 操作を続ける。 | 支援を続ける。 | 画面を定期取得する。5秒間隔は検証候補とする。 |
| 14 | 問題解決 | 解決を確認し、待つ。 | ガイドを作るか選択する。 | 家族側へガイド作成の確認を表示する。 |
| 15A | ガイドを作らない | 終了する。 | 「作成しない」を選ぶ。 | 支援セッションを終了する。 |
| 15B | ガイドを作る | ガイド作成・レビューへ進む。 | 「作成する」を選ぶ。 | ガイド作成フローへ移る。 |

### 5.1 このフローで未決定のこと

- 左端4pxバーが、利用者に発見でき、通常操作を邪魔しないか
- コメント入力が利用者にとって負担にならないか
- 家族が対応できるまでの待機画面、取消、再通知、対応予定時刻
- 時間制限がある認証コード問題で、後からの支援が間に合わない場合の案内
- 家族が発信したとき利用者がPCの前にいない、または応答しない場合の戻り先
- 接続時に画面共有を自動開始するか、利用者の確認を挟むか
- マーキングの種類、表示時間、消去条件、座標のずれへの対処
- どちらが支援を終了できるか、片方だけ終了した場合の扱い
- 定期取得が必要か、また5秒間隔が性能・プライバシー・ガイド品質の面で適切か

## 6. ガイド作成の正常系

**全体ステータス: 仮決定 / 次に確定する対象**

### 6.1 現在のフロー案

| # | 出来事 | 利用者（祖父） | 家族 | Mite |
| --- | --- | --- | --- | --- |
| 1 | 作成判断 | 家族の判断を待つ。 | 支援後、今回の内容を残すか判断する。 | 家族側へ作成確認を表示する。 |
| 2 | 下書き作成 | 待つ。 | 待つ、または必要情報を補う。 | 支援記録からスクリーンショットと説明を持つ仮ガイドを作る。 |
| 3 | レビュー | 家族と一緒に内容を見る。現案では祖父側から操作しない。 | 内容を確認し、ページを進める。 | 両者へ同じ仮ガイドを表示する。 |
| 4 | 修正 | 現案では閲覧のみ。 | 許可された項目を修正する。具体的な編集対象は未決定。 | 編集結果をプレビューへ反映する。 |
| 5 | 保存 | 保存完了を確認する。 | 保存を確定する。 | ガイドを保存し、支援セッションを終了する。利用者側への反映時期は未決定。 |

[SF]では、祖父と家族が一緒にレビューし、祖父側は操作せず家族側が編集・ページ移動する案になっている。一方で、AI出力の精度によってはレビュー自体をなくす可能性も注記されているため、現在案として検証する。

### 6.2 保存するかどうかの判断方針

**ステータス: 確定（方針レベル）**

保存の要否はAIではなく、利用者を知る家族が判断する。今後繰り返し役立つ支援だけを残し、一覧に不要なガイドを増やさない。

保存しない候補は次のとおりである。

- 一度しか起きない問題
- 毎回、解決方法が変わる問題
- 機器故障
- 次回ガイドを見ても、利用者だけでは対応しにくい問題

根拠: [PS]「繰り返し起きる操作を手順として残す」「一度きりの予期しない問題を解決する」

### 6.3 下書き材料の候補

| 情報 | 現在の扱い |
| --- | --- |
| 支援依頼時の画面 | 仮決定。最初の状況把握に使う。 |
| 支援中の画面 | 定期取得は仮決定。5秒間隔は検証候補であり、頻度・選定方法は未決定。 |
| 家族が示した場所 | ガイド材料の候補。保存形式は未決定。 |
| 操作した順番 | ガイド材料の候補。取得方法は未決定。 |
| 家族の説明 | ガイド材料の候補。音声をどう記録・文章化するかは未決定。 |
| 困りごとのコメント | ガイドの目的やタイトル作成に使える可能性があるが、用途は未決定。 |

### 6.4 AI利用の扱い

ガイド作成自体はMiteの中核だが、**AIによる自動生成をMVPの必須条件とはまだしない**。

- [SF]ではMiteが仮ガイドを作る。内部方式は明記されておらず、「AIの出力精度によってレビューをなくすかもしれない」という注記から、AI利用も検討対象と読み取れる。
- 一方、[PS]の更新判断では「ガイドを作成するときのAI支援」は追加検討事項であり、LLMへ画面情報を送ることへの懸念も示されている。
- したがって、まず「下書きが存在し、確認・修正・保存できる体験」をプロトタイプする。
- AI、ルールベース、手動作成のどれを採るかは、保存情報と情報保護方針を決めた後に技術調査する。

### 6.5 次に決める質問

- 作成判断は支援終了前か、終了後に家族だけで行うか
- 下書き生成を待つ間、利用者と家族を接続したままにするか
- 仮ガイドを誰が見る必要があるか
- 祖父側はレビュー中に閲覧だけとするか、ページ移動やコメントを許可するか
- 家族の負担を減らすため、レビュー・修正・保存をどこまで省略できるか
- 文章、画像、順番、タイトルのうち何を編集できるか
- 1ステップをどの規則で分割するか
- 保存後にすぐ利用者側へ反映するか
- 既存ガイドと重複した場合、追加・上書き・別保存のどれにするか

## 7. ガイド利用の正常系

**全体ステータス: 仮決定 / 次に確定する対象**

### 7.1 現在のフロー案

1. 後日、利用者が同じ、または似た操作を行いたいと考える。
2. Miteを開き、「手順を見る」を選ぶ。
3. 保存済みガイドの一覧を見る。
4. 理解しやすいタイトルと代表スクリーンショットから目的のガイドを選ぶ。
5. ガイドを開始し、最初のステップを表示する。
6. 説明とスクリーンショットを見て、実際のPC画面を操作する。
7. 次のステップへ進む。
8. すべてのステップを終えるまで繰り返す。
9. 完了表示を確認してガイドを終了する。

ガイドの表示例は次のような形を想定する。

```
STEP 1 / 4

画面下にある青い「Chrome」のマークを押してください。

[スクリーンショット]

[家族に聞く]                         [次へ]
```

### 7.2 表示方法の第一候補

**ステータス: 仮決定**

ガイドを小さなウィンドウとして操作画面の端に常駐させ、利用者が自分で「次へ」を押す方式を、最初のプロトタイプ候補とする。

この案は、別ページの説明書と操作対象の画面を何度も行き来する負担を減らせる。一方、画面を隠す、最前面表示が邪魔になる、「次へ」を押す操作自体が増えるというリスクがあるため、確定前に検証する。

### 7.3 ガイドから家族支援への切替

**ステータス: 確定（体験方針） / 仮決定（操作詳細）**

ガイドで分からなくなった場合、単なるエラーではなく正常なフォールバックとして家族支援へ移る。

支援依頼に引き継ぐ情報の候補は次のとおりである。

- ガイドID・タイトル
- 現在のステップ番号
- 現在表示している説明と画像
- 利用者の現在画面
- 利用者が入力した任意コメント

MVPでは遠隔操作ではなく、Flow Aの画面共有・音声・マーキング支援へ切り替える。

### 7.4 次に決める質問

- ガイドが増えても、一覧から目的のものを見つけられるか
- タイトルだけで分かるか、代表画像・カテゴリ・最近使った順が必要か
- 「認証コード」のようにサービスをまたいで一つにするか、Amazon・JALなどサービス別にするか
- ガイドウィンドウをどこに、どの大きさで表示するか
- 対象アプリとMiteを迷わず行き来できるか
- 「次へ」「戻る」「中断」「最初から」のどれが必要か
- 操作できたことを自動検知する必要があるか
- 途中終了したガイドを再開できるようにするか
- 完了を誰が、何をもって判断するか
- 家族支援へ切り替えた後、元のガイドへ戻るか、ガイドを更新するか

## 8. 状態設計

```

→ 支援依頼作成中
→ 支援待ち
→ 発信中／着信中
→ 接続中
→ 支援中
```

## 9. 分岐・異常系・状態ズレ

**ステータス: 未決定 / 正常系のプロトタイプ後に策定**

### 9.1 正常な分岐として扱うもの

- 家族がすぐ支援できる / 後から支援する
- 待っている間に利用者が自力解決する
- 家族が発信したとき、利用者がPCの前にいる / いない
- 支援後にガイドを作る / 作らない
- 仮ガイドをそのまま保存する / 修正して保存する / 破棄する
- ガイドを最後まで使う / 中断する / 家族支援へ切り替える

### 9.2 優先して扱う異常系

#### 支援依頼

- スクリーンショット取得失敗
- 支援依頼送信失敗
- ネット接続なし
- ボタン連打による重複依頼
- すでに依頼中の状態で再度依頼

#### 接続開始

- 利用者が応答しない
- 利用者がオフライン
- 接続失敗
- 接続中にアプリが終了する

#### 支援中

- 通信全体が切れる
- 音声だけ切れる
- 画面共有だけ止まる
- マーキングが届かない、または位置がずれる
- 画面解像度、表示倍率、ウィンドウ位置が変わる
- 片方のアプリだけが終了する

#### ガイド

- 下書き作成失敗
- 必要なスクリーンショットが足りない
- 下書きの内容が不適切
- 保存失敗
- 保存済みだが利用者側へ反映されない

### 9.3 状態ズレ

特に次の不一致を検討する。

- 家族側は「支援中」、利用者側は「接続中」
- 家族側には依頼が残っているが、利用者は自力解決済み
- 片方だけ支援終了済み
- 片方では音声接続済みだが、もう片方では未接続
- ガイドは家族側で保存済みだが、利用者側では未反映

各ケースを次の様式で決める。

| 場面 | 起きたこと | 種類 | 利用者側表示 | 家族側表示 | 復旧方法 | 最終状態 |
| --- | --- | --- | --- | --- | --- | --- |
| 例: 支援依頼後 | 利用者が自力解決 | 分岐 | 未決定 | 未決定 | 依頼取消候補 | 未決定 |
| 例: 接続中 | 通信失敗 | 異常 | 未決定 | 未決定 | 再試行候補 | 未決定 |
| 例: 支援中 | 片方だけ終了 | 状態ズレ | 未決定 | 未決定 | 安全に終了する候補 | 未決定 |

## 11. UI/UX要件

### 11.1 確定している設計原則

- 目的が一目で分かる大きなボタンを中心にする。

- 展開パネルのボタン名を理解できるか
- コメント入力は必要か、音声や選択肢の方がよいか

## 12. プロトタイプ検証方針

### 12.1 目的

プロトタイプを「完成版の小型版」ではなく、仕様の不足を発見する道具として使う。

最初に検証するのは、実通信・AI精度・サーバーではなく次の点である。

- 操作の順番が自然か
- 各時点で、利用者と家族が次に何をすればよいか分かるか
- 待機、接続、支援、レビュー、完了の状態が伝わるか
- ガイド作成の工程が家族にとって重すぎないか
- ガイドを利用者が見つけ、理解し、実際の操作へ移せるか
- ガイドで詰まったとき、説明をやり直さず家族支援へ移れるか

### 12.2 次の検証シナリオ

認証コードの確認後、元の購入画面へ戻るケースを代表シナリオとする。

1. 家族支援で元の購入画面へ戻り、問題を解決する。
2. 家族が「今後も必要」と判断してガイド作成を選ぶ。
3. 仮ガイドを確認・必要に応じて修正して保存する。
4. 後日、利用者が保存済みガイドを一覧から見つける。
5. ガイドを画面端に表示し、1ステップずつ操作する。
6. 完了できるか確認する。
7. 途中で分からないケースでは、「家族に聞く」へ切り替える。

### 12.3 検証記録の様式

| 仮説 | プロトタイプ上の案 | 観察すること | 成功条件 | 結果 | 仕様への反映 |
| --- | --- | --- | --- | --- | --- |
| ガイドを一覧から見つけられる | タイトル＋代表画像 | 探し方、迷い、所要時間 | 未決定 | 未実施 | 未実施 |
| 小型ガイドなら画面移動に迷わない | 右上に常駐 | 視線、ウィンドウ切替、邪魔さ | 未決定 | 未実施 | 未実施 |
| 家族のレビュー負担が小さい | 下書き→確認→保存 | 操作数、所要時間、修正箇所 | 未決定 | 未実施 | 未実施 |

検証後、各仮説を「採用」「変更」「保留」「棄却」のいずれかに分類し、本書へ反映する。

## 15. 今後の仕様策定フロー

今後は次の順番で進める。後工程の判断に必要な情報を前工程で作るため、原則として順序を入れ替えない。

### Step 1: ガイド作成 → ガイド利用の正常系を決める

**作るもの**

- 利用者・家族・Miteの3レーンフロー
- ガイド作成・レビュー・保存の画面遷移
- ガイド一覧・利用・完了・家族支援への切替フロー
- 各操作の担当者、入力、出力
- 正常時の状態候補
- 未決定事項一覧

**完了条件**

支援で解決した内容をガイドにし、後日利用者がそのガイドを使い終えるまでを、途中の画面と担当者を含めて説明できる。

### Step 2: プロトタイプで正常系を検証する

**作るもの**

- 実通信・AI・サーバーをモックにした操作プロトタイプ
- 検証仮説、観察結果、所要時間、迷った箇所
- 「採用・変更・保留・棄却」の判断

**完了条件**

少なくとも、ガイドの発見、内容理解、操作画面との行き来、ステップ移動、家族への切替、家族のレビュー負担について判断できる。

### Step 3: 分岐・異常系・状態ズレを決める

**作るもの**

- 正常な分岐一覧
- 優先度付き異常系一覧
- 支援依頼・接続・支援・ガイドの状態遷移表
- 利用者側と家族側の表示
- 再試行、取消、タイムアウト、再接続、最終状態

**完了条件**

各ケースについて、両者に何が見え、何を操作でき、最終的にどの状態へ収束するか説明できる。

### Step 4: 保存情報を決める

**作るもの**

- 取得する情報と取得しない情報の一覧
- 取得目的、閲覧者、編集者、保存場所、保存期間、削除方法
- 同意、マスキング、AI送信、暗号化、アクセス制御の方針
- ガイドを作らない場合と作る場合のデータ処理

**完了条件**

すべての取得候補について、なぜ必要か、誰が見られるか、いつ消すかを説明できる。

### Step 5: 技術調査を行う

**作るもの**

- 実現可否と制約
- 技術候補の比較
- 小さな検証結果
- MVPで採用する候補と、採用しない候補
- 残るリスク

**完了条件**

体験仕様を実現する方式を選ぶための判断材料がそろい、実現できない仕様が洗い出されている。

### Step 6: 技術設計へ落とす

**作るもの**

- アーキテクチャ
- 状態機械
- データモデル
- API・リアルタイムイベント
- セキュリティ・エラー処理・テスト方針
- 実装タスクへの分解

**完了条件**

実装担当が、プロダクト上の判断を勝手に補わずに開発へ着手できる。
