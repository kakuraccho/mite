# 未決定事項

この文書は、Miteの仕様探索中に検証する疑問を記録する。ここに書かれた「仮動作」はプロトタイプを最後まで操作可能にするためのものであり、最終仕様ではない。

## Q-001: 約4pxの画面端を祖父が見つけ、狙って操作できるか

- 状況: 通常操作を邪魔しない細さと、発見・ポインティングしやすさが競合する
- プロトタイプ上の仮動作: 画面左端に細いバーを常時見せ、ホバーできる領域は視覚上の線より広めに取る
- 他の候補: バーを太くする、常時小さな取っ手を出す、画面隅に固定ボタンを置く、ショートカットキーを併設する
- 判断方法: ユーザー検証
- 状態: 未決定

## Q-002: ホバーでパネルが開くことを祖父が理解できるか

- 状況: クリック前に機能が隠れているため、存在や開き方に気づかない可能性がある
- プロトタイプ上の仮動作: バーへのホバーまたはキーボードフォーカスで支援パネルを展開する
- 他の候補: クリックで開閉する、初回だけ説明を出す、常時ラベルを見せる
- 判断方法: ユーザー検証
- 状態: 未決定

## Q-003: 画面端のバーや展開パネルが通常のPC操作を邪魔しないか

- 状況: 左端のスクロール、アプリのメニュー、ウィンドウ操作と競合する可能性がある
- プロトタイプ上の仮動作: バーは細くし、パネルはポインターが離れると閉じる一時表示にする
- 他の候補: 表示位置を選べるようにする、一定時間後だけ閉じる、明示的な閉じるボタンを使う
- 判断方法: ユーザー検証
- 状態: 未決定

## Q-004: 「困りごとを記録する」という言葉で目的が伝わるか

- 状況: 支援を依頼する操作だと理解されない、または録音機能だと誤解される可能性がある
- プロトタイプ上の仮動作: ボタン文言を「困りごとを記録する」とし、次画面で家族へ送ることを説明する
- 他の候補: 「家族に助けをたのむ」「この画面を家族に見せる」「困った画面を送る」
- 判断方法: ユーザー検証
- 状態: 未決定

## Q-005: 困った瞬間と家族が支援する瞬間を分けても価値があるか

- 状況: 家族がすぐ応答できない場合、画面記録とコメントだけで後から状況を再現できる必要がある
- プロトタイプ上の仮動作: 依頼を送信したあとも未解決として残し、家族が後から内容を見て発信できる
- 他の候補: 即時通話だけにする、対応予約を作る、非同期の文章回答だけを返す
- 判断方法: ユーザー検証
- 状態: 未決定

## Q-006: オンライン状態を見て家族から電話する流れが自然か

- 状況: 「オンライン」が応答可能を意味するとは限らず、家族が発信をためらう可能性がある
- プロトタイプ上の仮動作: 祖父を常に「オンライン」と疑似表示し、家族が任意のタイミングで発信する
- 他の候補: 「操作中」「応答できそう」「最終利用時刻」を出す、祖父が通話希望時間を指定する
- 判断方法: ユーザー検証
- 状態: 未決定

## Q-007: 家族が置いたマーカーはいつ消えるべきか

- 状況: すぐ消えると見逃し、残り続けると次の案内や画面操作を邪魔する
- プロトタイプ上の仮動作: 最新のマーカー一つだけを表示し、次のマーカーまたは支援終了で置き換え・消去する
- 他の候補: 数秒後に自動で消す、祖父が消す、家族が明示的に消す、複数を番号付きで残す
- 判断方法: ユーザー検証
- 状態: 未決定

## Q-008: 支援を終了するのは祖父と家族のどちらが自然か

- プロトタイプ上の仮動作: 正常系では家族が「支援を終了する」を押してガイド作成判断へ進む
- 他の候補: 祖父だけが終了する、双方に終了操作を置く、相互確認後に終了する
- 判断方法: ユーザー検証
- 状態: 未決定

## Q-009: ガイドを残すか誰が判断するか

- 状況: 再発しそうかを家族が判断しやすい一方、祖父にとって必要かは本人にしか分からない場合がある
- プロトタイプ上の仮動作: 家族が支援終了後に「ガイドを作成する / 作成しない」を選ぶ
- 他の候補: 祖父が選ぶ、双方へ確認する、一定条件で自動提案する
- 判断方法: ユーザー検証
- 状態: 未決定

## Q-010: 家族によるガイド編集が負担にならないか

- プロトタイプ上の仮動作: 固定データからタイトルと3手順を自動入力した体にし、家族は少ない入力欄だけを編集する
- 他の候補: 編集せず保存する、音声から下書きする、後で編集する、画像と短いメモだけを残す
- 判断方法: ユーザー検証
- 状態: 未決定

## Q-011: 祖父側は読み取り専用のガイド確認で十分か

- 状況: 誤りに気づいても祖父側から修正や差し戻しができず、確認したことも家族へ伝わりにくい可能性がある
- プロトタイプ上の仮動作: 祖父側は読み取り専用で内容を確認し、編集と保存は家族側だけで行う
- 他の候補: 修正依頼ボタンを置く、祖父も編集できる、読み上げと確認完了ボタンを加える

## Q-012: 祖父が着信に応答しなかったらどうするか

- プロトタイプ上の仮動作: タイムアウトを実装せず、祖父が応答するまで着信状態を保つ
- 他の候補: 一定時間後に着信を閉じる、再発信する、通知を残す、時間を予約する
- 判断方法: ユーザー検証

## Q-013: コメントが空でも支援依頼を送れるか

- プロトタイプ上の仮動作: コメントなしでも送信でき、ダミーの記録画面は必ず添付する
- 他の候補: 一言の入力を必須にする、選択式の困りごとを加える、音声メモを許可する

## Q-014: 未解決の依頼がある状態で新しい依頼を作れるか

- 他の候補: 依頼一覧を持つ、既存依頼へ画像やコメントを追加する、古い依頼を自動で閉じる
- 判断方法: プロダクト判断

## Q-015: リロードや複数タブの競合をどう扱うか

- 状況: 個別ルートの疑似同期中にリロードや同時操作があると、状態やイベント順序が食い違う可能性がある
- プロトタイプ上の仮動作: 同一ブラウザ内だけで `BroadcastChannel` と `localStorage` を使い、最後に届いた状態を採用する
- 他の候補: `/demo` だけを検証対象にする、タブごとの所有権を決める、本番サーバーで整合性を保証する
- 判断方法: 技術調査
- 状態: 未決定

## Q-016: 通知配送・接続・ガイド生成の待機や失敗をどう伝えるか

- 状況: 実環境では遅延や失敗が起こるが、長い待機が不安を生み、再操作による重複も起こり得る
- プロトタイプ上の仮動作: 通知配送と接続は短い固定のモック遅延後に必ず成功させ、ガイドは固定のひな形をすぐ表示する
- 他の候補: 手動で成功・失敗を切り替える開発操作を置く、再試行とキャンセルを用意する、段階ごとに制限時間を設ける
- 判断方法: 技術調査
- 状態: 未決定

## Q-017: 共有画面と祖父側で異なるサイズでもマーカー位置を一致させられるか

- 状況: ウィンドウ比率、拡大率、DPI、スクロール位置が違うと、同じ座標が同じ操作対象を指さない
- プロトタイプ上の仮動作: 同じ縦横比のダミー画面内でクリック位置を割合として扱う
- 他の候補: 操作対象の要素IDを送る、画面変化ごとに座標を補正する、表示サイズを固定する
- 判断方法: 技術調査
- 状態: 未決定

## Q-019: 支援依頼・画像・ガイドをどのくらい保存するか

- 状況: 後日の支援には履歴が役立つ一方、個人情報を含む画面データの長期保存はリスクになる
- プロトタイプ上の仮動作: 架空データだけをブラウザ内で一時的に扱い、外部や永続サーバーには保存しない
- 他の候補: 支援終了時に削除する、期間を決めて保存する、画像を保存せずガイドだけ残す、本人が削除できるようにする

## Q-020: 着信や状態変化のとき、キーボードフォーカスをどこへ移すか

- 状況: 着信に気づきやすくするには応答ボタンへの移動が役立つ一方、祖父が別の入力中なら操作を奪う可能性がある。`/demo` では反対側ペインの操作も妨げ得る
- プロトタイプ上の仮動作: 状態変化を見出しと文字で明示するが、フォーカスは自動移動させず、通常のTab操作で主要ボタンへ移れるようにする
- 他の候補: 着信時だけ応答ボタンへ移す、音やWindows通知を併用する、利用者設定で切り替える
- 判断方法: ユーザー検証
- 状態: 未決定

## Q-021: 家族が編集中のガイドを祖父側へいつ反映するか

- 状況: 入力中から見えると共同確認しやすい一方、未完成の文章や一時的な空欄を祖父へ見せて混乱させる可能性がある
- プロトタイプ上の仮動作: 入力値は変更ごとに共有状態へ反映するが、祖父側には家族が確認を依頼して `guideReview` になってから表示する
- 他の候補: 一文字ごとにプレビューする、入力欄を離れたときに反映する、家族が「下書きを送る」を押したときだけ反映する
- 判断方法: ユーザー検証
- 状態: 未決定

## Q-022: 支援依頼の作成中や着信中に取り消したい場合をどう扱うか

- 状況: 誤ってパネルを開いた、困りごとが自己解決した、今は通話できない、といった場合に正常系以外の戻り先が必要になる
- プロトタイプ上の仮動作: 第一段階では個別のキャンセル遷移を作らず、開発用の「最初からやり直す」で初期状態へ戻す
- 他の候補: 下書きを破棄して閉じる、依頼を解決済みにする、着信を拒否して依頼だけ残す、あとでかけ直す意思を伝える
- 判断方法: プロダクト判断
- 状態: 未決定
