# Mite プロトタイプ開発指示

## 現在の目的

このリポジトリでは、Mite（ミテ）の**仕様探索用プロトタイプ**を作る。

目的は本番品質のアプリを完成させることではない。祖父側と家族側の体験を実際に触れる形にし、足りない画面・状態・分岐・疑問点を発見することが目的である。

優先順位は次のとおり。

1. 正常系を最初から最後まで早く通す
2. 状態遷移をユーザーと開発者の両方から確認できるようにする
3. 後から差し替えられるモックで実装する
4. 未決定事項を黙って最終仕様にせず、記録する
5. 本番インフラや難しい技術を先回りして作らない

最終的な製品は祖父側・家族側ともにWindowsアプリを想定している。ただし、今回のプロトタイプの技術構成を本番の技術選定とはみなさない。

## プロダクトの背景

Miteは、高齢のPC利用者が、信頼する家族から離れた場所でも支援を受けられるようにするサービスである。家族がすべてを代わりに操作するのではなく、できる部分は本人が操作する。

### 祖父側

- 80歳で、普段からPCを使って買い物や航空券予約などを行う
- マウス操作や文字入力そのものができないわけではない
- 見慣れない画面や、複数画面を行き来する場面で止まりやすい
- 主な負担は、**次に何をどの順番で行うか判断すること**である

### 家族側

- 祖父のPC操作を支援できる家族
- 離れて暮らしていたり、困った瞬間にすぐ対応できなかったりする

### 大切にする価値

- 本人ができることは奪わない
- 助けを求めるための難しい操作を増やさない
- 信頼・安心・判断は人が担う
- AIは人を置き換えず、整理や反復作業を補助する
- 一度の支援を、次回にも使える形へつなげる

## 現在想定している正常系

以下は確定仕様ではなく、プロトタイプで検証する仮説である。

1. 祖父がPC操作で困る
2. 祖父が画面左端の細いバーへマウスを移動する
3. 一時的に展開したパネルから「困りごとを記録する」操作を行う
4. Miteがスクリーンショットを撮った体で、任意コメントの入力画面を表示する
5. スクリーンショットとコメントを一つの支援依頼として保存する
6. 家族側へ支援依頼の通知が届く
7. 家族は依頼内容と祖父のオンライン状態を確認する
8. 家族が対応可能なタイミングで、Miteから祖父へ電話をかける
9. 祖父が電話に出る
10. 支援セッションを開始する
11. 家族側に祖父の画面を模した共有画面を表示する
12. 家族が共有画面上をクリックすると、祖父側の同じ位置にマーカーを表示する
13. 音声通話中であることだけをUIで表現する
14. 祖父が家族の案内を受けながら自分で操作する
15. 解決後、家族がガイドを作るか選ぶ
16. 作らない場合は接続を終了する
17. 作る場合は、記録したという体の画像から仮ガイドを作る
18. 家族が仮ガイドを編集し、祖父側では読み取り専用で確認する
19. ガイドを保存して接続を終了する

最初は、この正常系を一度最後まで通せる状態にする。

## 今回の実装範囲

実装するもの：

- 祖父側画面と家族側画面
- 画面左端の細いバーと、ホバー時に展開する支援パネル
- 祖父側からの支援依頼作成
- 任意コメント入力
- 家族側への支援依頼通知の疑似表示
- 祖父のオンライン状態の疑似表示
- 家族側からの発信
- 祖父側の着信・応答
- 接続中、支援中、ガイド作成判断中、レビュー中、終了済みなどの状態表示
- 祖父の画面共有を模したサンプル画面
- 家族側のクリックに応じたマーキング
- 祖父側への疑似リアルタイム反映
- 「ガイドを作成する / 作成しない」の分岐
- 仮ガイドの疑似生成
- 家族側でのガイド編集
- 祖父側でのガイドプレビュー
- ガイド保存と支援終了
- 最初から試し直せるリセット機能
- 現在の状態と直近イベントを確認できる開発用表示

次はモックで表現し、実機能を作らない：

- Windows画面の実キャプチャ
- デスクトップ全体への実オーバーレイ
- 実通知
- 実音声通話
- ネットワーク越しの実画面共有
- AIによる実ガイド生成
- 実オンライン判定
- 実スクリーンショットの定期保存

実際の画面・マイク・カメラ権限を要求してはいけない。

## 今回は実装しないもの

ユーザーが明示的に範囲を変更しない限り、次を追加しない。

- 遠隔操作
- 支援中のインカメラ映像
- 音声文字起こし
- ガイド利用中のAI支援
- ガイドのAI検索
- 本番用の認証・認可
- 本番用サーバー・データベース
- 実際の個人情報や画面データの保存
- WindowsのUACや管理者権限への対応
- 配布、自動更新、本番運用

## 技術上の既定方針

既存リポジトリに技術構成がある場合は、それを優先する。

リポジトリが空の場合は、仕様検証の速さを優先して次を使う。

- React
- TypeScript
- Vite
- 通常のCSSまたはCSS Modules
- React Reducerまたは小さなローカルストア
- Vitest

推奨ルート：

- `/grandfather`：祖父側
- `/family`：家族側
- `/demo`：両方を並べて確認する画面

別タブ間の疑似同期は、可能なら `BroadcastChannel` を使う。難しければ `localStorage` イベント、または `/demo` 内の共有状態でよい。

依存関係は最小限にする。これは本番Windowsアプリの技術選定ではない。

## 状態設計

場当たり的なbooleanを増やさず、支援セッションの状態をReducerなど一か所で管理する。

最低限、次の状態を扱う。

- `idle`
- `requestDraft`
- `requestSent`
- `waitingForFamily`
- `familyViewingRequest`
- `incomingCall`
- `connecting`
- `inSession`
- `guideDecision`
- `guideDraft`
- `guideReview`
- `completed`

イベント例：

- `OPEN_REQUEST_PANEL`
- `SUBMIT_SUPPORT_REQUEST`
- `VIEW_SUPPORT_REQUEST`
- `START_CALL`
- `ACCEPT_CALL`
- `CONNECTION_ESTABLISHED`
- `PLACE_MARKER`
- `END_SUPPORT`
- `CHOOSE_CREATE_GUIDE`
- `CHOOSE_SKIP_GUIDE`
- `UPDATE_GUIDE_STEP`
- `SAVE_GUIDE`
- `RESET_DEMO`

UIコンポーネントはイベントを送るだけにし、ドメイン状態を直接書き換えない。

## UI・UX方針

### 祖父側

- 短く平易な日本語を使う
- 「セッション」「キャプチャ」などの専門用語を画面に出さない
- ボタンを大きくし、一画面の選択肢を増やしすぎない
- 今何が起きているか、次に何をすればよいかを常に示す
- 家族との接続中・画面共有中であることを明確にする
- 取り消し・終了操作を見つけやすくする

### 家族側

- 支援依頼、記録時刻、コメント、画像、祖父の状態を把握しやすくする
- 発信、マーキング、終了、ガイド作成の操作を明確に分ける
- ガイド確認・編集を少ない操作で終えられるようにする

### 共通

- 色だけで状態を表現しない
- キーボードフォーカスを見えるようにする
- クリック対象を十分な大きさにする
- 見た目の作り込みより、フローの理解を優先する

## デモ用シナリオ

祖父が航空券を購入中、認証コードを確認するためにメール画面へ移動した。その後、元の購入画面へ戻る方法が分からなくなった。

支援依頼のサンプル：

- コメント：「番号は分かったけれど、飛行機の画面に戻れません」
- 記録画面：メール画面を模したダミー画面
- 祖父の状態：オンライン

支援中は、メール画面とタスクバーを模した画面を使う。家族がタスクバー付近をクリックすると、対応する位置へ目立つマーカーを表示する。

ガイドタイトル：

「認証コードを確認したあと、元の画面へ戻る」

ガイド手順：

1. 画面下のタスクバーを見ます。
2. 飛行機の購入画面のアイコンを押します。
3. 元の画面に戻ったら、控えた番号を入力します。

## 未決定事項の扱い

書かれていない挙動を、Codexが黙って最終仕様として確定してはいけない。

ただし、すべての疑問で停止する必要もない。後から変えられる仮動作を置き、その仮定を記録する。

`docs/open-questions.md` を作り、各項目に次を書く。

- 状況
- プロトタイプ上の仮動作
- 他の候補
- 判断方法：`プロダクト判断`、`ユーザー検証`、`技術調査`、`MVP外`
- 状態

例：

```md
## Q-001: 祖父が着信に応答しなかったらどうするか

- 状況: 支援依頼は残っているが、祖父が離席している可能性がある
- 仮動作: 一定時間後に着信を閉じ、依頼は未解決のまま残す
- 他の候補: 再発信、通知を残す、時間を予約する
- 判断方法: ユーザー検証
- 状態: 未決定
```

`docs/decisions.md` も作り、仮決定・確定判断と理由を記録する。

プロトタイプ中に新しい分岐や異常系を発見したら、実装を膨らませる前に `docs/open-questions.md` へ追加する。

特に検証したい疑問：

- 約4pxの画面端を祖父が見つけ、狙って操作できるか
- ホバーでパネルが開くことを理解できるか
- 通常のPC操作を邪魔しないか
- 「困りごとを記録する」という言葉で目的が伝わるか
- 困った瞬間と支援する瞬間を分けても価値があるか
- オンライン状態を見て家族から電話する流れが自然か
- マーカーはいつ消えるべきか
- 支援を終了するのは祖父と家族のどちらが自然か
- ガイドを残すか誰が判断するか
- 家族のガイド編集が負担にならないか
- 祖父側は読み取り専用の確認で十分か

## 実装ルール

- モックデータだけを使い、実際の個人情報を入れない
- 外部サービスへデータを送らない
- APIキーを要求しない
- モックサービスを小さなインターフェースの後ろへ置く
- UIと状態遷移ロジックを分離する
- 主要な状態遷移と正常系に単体テストを付ける
- 変更後はbuild、test、lintを実行する
- 実行できなかったコマンドや残った問題を正直に報告する
- 過剰な抽象化、拡張性対応、本番品質の先回りをしない

## 第一段階の完了条件

次を最初から最後まで実行できること。

1. 祖父側と家族側を開く
2. 祖父側で画面左端のパネルを開く
3. 支援依頼を作成・送信する
4. 家族側で依頼を確認する
5. 家族側から電話をかける
6. 祖父側で電話に出る
7. 支援中画面へ移る
8. 家族側で共有画面をクリックし、祖父側へマーカーを表示する
9. 支援を終了し、ガイド作成を選ぶ
10. 家族側で仮ガイドを編集する
11. 祖父側で内容を確認する
12. 保存・終了し、リセットして再実行する

あわせて次を用意する。

- `README.md`：起動方法、コマンド、デモ手順
- `docs/open-questions.md`：発見した疑問
- `docs/decisions.md`：仮決定と理由
- 状態遷移テスト

## Codexの進め方

1. リポジトリと適用される指示ファイルを確認する
2. 実装前に短い計画を示す
3. 個別画面の作り込みより先に正常系を縦に通す
4. 状態遷移と疑似同期を一か所へ集約する
5. 最低限のUIを整える
6. テストを追加する
7. README、疑問、判断の文書を更新する
8. 検証コマンドを実行し、結果を報告する

すべての曖昧さで止まらない。後から変えられる仮動作を置き、「仮」であることを文書化する。
