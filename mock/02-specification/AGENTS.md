# Mite モック開発リポジトリ指示

## 1. このリポジトリの目的

このリポジトリでは、Mite（ミテ）の**仕様探索用モック**を実装する。

目的は本番品質のWindowsアプリを完成させることではない。祖父側と家族側の正常系を触れる形にし、画面・状態・操作順・未決定事項を検証できるようにすることが目的である。

今回通す正常系は、次の3本である。

1. 困りごとの記録から、家族による支援、支援終了まで
2. 支援内容から仮ガイドを作成し、家族と祖父が確認して保存するまで
3. 保存済みガイドを祖父が選び、手順に沿って操作するまで。途中で分からなくなった場合は遠隔支援へ移る

## 2. 作業開始前に読むもの

実装前に、必ず次の順で読むこと。

1. この `AGENTS.md`
2. `specs/README.md`
3. `specs/00-overview.md`
4. `specs/01-state-model.md`
5. 実装対象に対応するフロー仕様
6. `specs/05-screens-and-ui.md`
7. `specs/06-mock-data-and-demo.md`
8. `specs/07-acceptance-criteria.md`
9. `specs/90-open-questions.md`
10. `specs/91-decisions.md`

製品の振る舞いは `specs/` を正とする。仕様同士が矛盾する場合は、勝手に解釈して固定せず、`specs/90-open-questions.md` に記録する。

## 3. 優先順位

優先順位は次のとおり。

1. 3本の正常系を最初から最後まで通す
2. 祖父側と家族側の状態が対応していることを確認できるようにする
3. 後から差し替えられる単純なモックで実装する
4. 状態遷移を一か所に集約し、場当たり的な条件分岐を増やさない
5. 未決定事項を見つけ、文書へ残す
6. 見た目を整える

個別画面を先に作り込まず、縦に一本通る実装を優先する。

## 4. 今回の実装範囲

実装対象は次のとおり。

- 祖父側画面
- 家族側画面
- 祖父側と家族側を同時に確認できるデモ画面
- 画面左端に常時表示する約20pxの操作領域
- 左端領域にマウスを乗せたときに展開するパネル
- 「困りごとを記録する」導線
- 「ガイドを見る」導線
- 困りごと記録時の疑似スクリーンショットと任意コメント
- スクリーンショットとコメントを使った疑似ガイド照合
- 類似ガイドがない場合の支援依頼作成と家族側通知
- 家族側での支援依頼確認と祖父の疑似オンライン状態表示
- 家族側からの疑似発信、祖父側の着信・応答
- 疑似画面共有
- 家族側でクリックした位置を祖父側へ表示するマーキング
- 支援中に5秒ごとに記録していることを示す疑似ログ
- 支援終了時の「ガイドを作成する / 作成しない」分岐
- 疑似的な仮ガイド生成
- 家族側での仮ガイド確認・編集
- 祖父側での読み取り専用プレビュー
- ガイド保存と接続終了
- 保存済みガイドの一覧、選択、1ステップずつの閲覧
- ガイドの前後ページ移動と完了
- ガイド利用中の「遠隔支援へ移る」導線
- デモのリセットとシナリオ切り替え
- 主要状態遷移のテスト

## 5. 今回は実装しないもの

明示的に範囲が変更されない限り、次を実装しない。

- 実際のWindows画面キャプチャ
- デスクトップ全体への実オーバーレイ
- 実際の音声通話
- 実際の通知
- ネットワーク越しの画面共有
- 実オンライン判定
- 実AIによる画像・文章解析
- 実AIによるガイド生成・検索
- 音声文字起こし
- 遠隔操作
- 支援中のインカメラ映像
- ガイド利用中のAI支援
- 本番用の認証・認可
- 本番用サーバー、データベース、クラウド保存
- 実際の個人情報、画面、音声の保存
- WindowsのUAC、管理者権限、配布、自動更新
- 網羅的な異常系・復旧処理

ブラウザの画面共有・マイク・カメラ・通知権限を要求してはいけない。外部APIやAPIキーも使用しない。

## 6. 技術上の既定方針

既存リポジトリに技術構成がある場合は、それを優先する。既存構成を大きく置き換える前に理由を示すこと。

リポジトリが空の場合は、仕様検証の速さを優先し、次を既定とする。

- React
- TypeScript
- Vite
- React Router
- 通常のCSSまたはCSS Modules
- React Reducer、Context、または同程度に小さい状態管理
- Vitest
- Testing Library

推奨ルートは次のとおり。

- `/grandfather`：祖父側
- `/family`：家族側
- `/demo`：祖父側と家族側を同時に並べる検証画面

`/demo` を最優先で完成させる。別タブ同期が必要な場合は、`BroadcastChannel`、`localStorage` イベント、または小さなモックストアを用いる。サーバーは作らない。

## 7. 状態管理のルール

- 支援依頼、支援セッション、ガイド作成、ガイド利用の状態を明示的に持つ
- 関連する状態を多数の独立booleanで表さない
- UIコンポーネントは、可能な限りイベントを送るだけにする
- 状態遷移と副作用を分離する
- マーカー座標は共有画面に対する相対座標で保持する
- デモの再現性を優先し、乱数や時刻依存を避ける
- 永続化はモックに必要な範囲だけ `localStorage` 等で行う

状態名とイベント名の基準は `specs/01-state-model.md` に従う。

## 8. UI・UXのルール

### 祖父側

- 短く平易な日本語を使う
- 一画面の主要操作を増やしすぎない
- 大きなボタンと十分な余白を使う
- 「今何が起きているか」「次に何をするか」を表示する
- 「セッション」「キャプチャ」「ストリーミング」などの専門用語を画面に出さない
- 家族との接続中、画面を見てもらっている状態を明確にする
- ガイドは1ステップずつ表示する
- 画面左端の操作領域は、通常操作を極力邪魔しない形で常時見えるようにする

### 家族側

- 支援依頼、記録時刻、コメント、疑似スクリーンショット、祖父の状態を一目で確認できるようにする
- 発信、マーキング、終了、ガイド作成を視覚的に分ける
- ガイド編集は少ない操作で終えられるようにする

### 共通

- 色だけで状態を表現しない
- クリック対象を十分な大きさにする
- キーボードフォーカスを見えるようにする
- ローディングや待機中は、何を待っているかを表示する
- ピクセル単位の完成度より、フローと状態の理解を優先する

## 9. モック実装の方針

実機能の代わりに、決定的なモックを使う。

- スクリーンショット：同梱したダミー画面またはCSSで作った画面
- ガイド照合：デモ設定の `match / no-match` で結果を決める
- 通知：家族側画面内の通知として表示
- オンライン状態：デモ設定で切り替える
- 通話：UI状態だけを切り替える
- 画面共有：同一のダミー画面を両側へ表示
- 定期スクリーンショット：5秒ごとに件数と時刻を記録するだけ
- AI生成：固定テンプレートから仮ガイドを生成

モックサービスは小さなインターフェースの後ろに置き、UIへ直接埋め込まない。

## 10. 未決定事項の扱い

書かれていない挙動を、Codexが黙って最終仕様として確定してはいけない。

ただし、すべての曖昧さで作業を停止しない。正常系を通すために必要な場合は、後から変更しやすい仮動作を置き、次を行う。

1. `specs/90-open-questions.md` に疑問を追加する
2. 仮動作を `specs/91-decisions.md` に「暫定」として記録する
3. 実装箇所に過剰な抽象化を入れず、変更しやすく保つ

新しい異常系を発見した場合も、今回の正常系に不可欠でなければ実装を膨らませず、まず疑問として記録する。

## 11. 実装の進め方

1. リポジトリ構成、既存コード、適用される指示ファイルを確認する
2. `specs/` を読む
3. 変更対象と短い実装計画を示す
4. `/demo` で正常系を縦に通す
5. 祖父側、家族側の個別ルートを整える
6. 主要状態遷移のテストを追加する
7. `specs/90-open-questions.md` と `specs/91-decisions.md` を更新する
8. build、test、lintを実行する
9. 実行結果、未完了事項、追加した疑問を報告する

大規模なリファクタリング、過剰な拡張性対応、本番インフラの先回りを行わない。

## 12. 完了条件

完了条件は `specs/07-acceptance-criteria.md` に従う。

最低限、次をデモできること。

1. 類似ガイドなし：困りごと記録 → 支援依頼 → 家族が発信 → 支援 → ガイド作成 → 保存
2. 類似ガイドあり：困りごと記録 → ガイド照合 → 該当ガイドを利用 → 完了
3. ガイド一覧から利用：ガイドを見る → 選択 → 1ステップずつ操作 → 完了
4. ガイド途中で支援：ガイド利用 → 遠隔支援へ移る → 支援依頼フローへ接続

検証後は、実行したコマンドと結果を正直に報告する。
